# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sumiran Lite is an offline-first Progressive Web App for logging daily "jaap" (mantra repetition count). Single-page vanilla JavaScript, no framework, no build step — `index.html`, `app.js`, `styles.css` are served as static files as-is. Live at https://arijeetkundu.github.io/jaap-ledger/, deployed via GitHub Pages from the `main` branch root.

## Commands

```bash
# Run locally (serve over HTTP — IndexedDB/PWA installability are unreliable on file://)
python -m http.server 3333
# open http://localhost:3333

# Test on a phone on the same Wi-Fi: http://<LAN-IP>:3333 (different origin from localhost — no shared IndexedDB/localStorage)

# Install test tooling
npm install

# Run the full test suite (requires the server above running in another terminal)
npm test

# Run a single suite
node tests/test.js              # structural smoke tests
node tests/test-unit.js         # pure-logic unit tests
node tests/test-e2e.js          # full user-flow E2E tests
node tests/test-redesign.js     # design tokens, milestone celebration, motion
node tests/test-splash-custom.js # custom splash image upload/rotation/delete
node tests/test-mala-mode.js    # Mala Mode: counting, additive commits, draft safety, backup compatibility
node tests/test-sunday-backup.js # Sunday backup modal + Google Drive backup (mocked network)
node tests/test-i18n.js         # language picker, Settings switcher, translations-load-failure fallback
node tests/test-service-worker.js # offline launch, precache, deploy pickup, shortcut target

# Lint (fast, no server needed, independent of npm test)
npm run lint
```

There is no build step and no CI pipeline — `npm test` and `npm run lint` must both be run locally before pushing. 577 assertions across the 9 suites as of this writing.

**This repo lives inside OneDrive, and that makes a full `npm test` run intermittently fail in ways the code did not cause.** Observed: `EPERM` when `test-service-worker.js` renames `styles.css` for its deploy simulation (OneDrive holding the file), and Puppeteer teardown errors ("Navigating frame was detached", "Target closed") aborting whichever suite happens to be running. The failure lands in a different suite each time and the suite passes when run on its own. Re-run the individual suite before believing a full-run failure, and don't report a flaky run as a clean one.

**Every browser context in every suite must call `seedAppState(page)` from `tests/test-helpers.js` before its first navigation.** That is the only shared module across the otherwise-standalone suites, and it earns the exception by being a correctness requirement rather than a convenience: it marks today's Sunday Backup Reminder as handled, and a context that omits it produces a run whose result depends on the day of the week. The modal is a real `position: fixed; inset: 0` backdrop at z-index 9800 — on a Sunday it opens over the whole app and silently swallows clicks meant for anything underneath (`#maintenance-toggle` above all), surfacing as a timeout that names the element it *couldn't* reach rather than the modal covering it. Two contexts had already drifted without it and the suite failed on a Sunday, having passed every day it happened to be run before.

**Lint is a correctness net, not a style checker.** `eslint.config.js` enables only rules that catch genuine mistakes (`no-undef`, `no-unreachable`, `no-dupe-keys`, unused vars, …) and deliberately no formatting/style rules — `app.js`'s conventions predate the config, and reformatting it would bury real findings in noise. Its real value in a no-modules codebase is catching a typo'd global, which nothing else here would. Two rules are switched off on purpose, both recorded in the config: **`no-implicit-globals` everywhere** (app.js's top-level functions and `let`s are *intended* to be globals — enabling it produced 103 errors, all false), and **`no-undef` in `tests/**`** (`page.evaluate()` callbacks are serialized and run in the page against `app.js`'s globals, which ESLint can't see). Lint is deliberately *not* wired into `npm test` — it stays a separate, fast, opt-in command.

## Architecture

**No modules.** All functions in `app.js` are top-level, global, and hoisted — execution order in the file matters (later code assumes earlier functions/constants already exist). There's no import/export boundary; naming collisions are prevented only by convention.

**Two-tier storage, strictly separated by purpose:**
- **IndexedDB** (`jaap-ledger-db`, `DB_VERSION` in `app.js`) holds practice data only, across 4 object stores: `ledger` (live entries), `ledger-backups` (latest auto-backup, overwritten each save), `meta` (currently unused — was a one-time data.json seeding guard, now dead schema kept per the never-destroy-stores rule below), `sankalpa` (single vow record). The upgrade handler is additive-only — bump `DB_VERSION` and add a store only if needed; never destroy existing stores.
- **localStorage** holds display preferences and device-local assets only, never practice data: `malaViewEnabled`, `backgroundChoice`, `lastSplashImage`, `lastMalaImage`, `splashImage:custom0`..`custom3`, `appLanguage`, `lastSundayBackupPromptDate`, `lastDriveBackupAt`, `textSize`, `syncEverSignedIn`, `syncPushPending`. Export/Import and the automatic backup cover the IndexedDB **ledger and Sankalpa** only — localStorage content is deliberately excluded and never round-trips through backup/restore. Note `lastSundayBackupPromptDate` (the Sunday prompt was dealt with — written by a successful upload *and* by every dismiss path, so it cannot tell you whether a backup happened) and `lastDriveBackupAt` (written *only* on a genuinely successful upload) are separate keys for exactly that reason — don't conflate them.

**Splash screen rotation runs synchronously before first paint.** A `chooseSplashImage()` IIFE at the top of `app.js` resolves the image pool and sets `#splash-img`/`#splash-source` before the async `initApp()` bootstrap even starts. Hanuman (`splash/hanuman-splash.*`) is a fixed constant, always in the pool, never stored, never replaceable. Up to 4 additional slots are user-uploaded photos; a slot's filled/empty state is simply whether `localStorage["splashImage:customN"]` holds a valid `data:image/` URL — there's no separate metadata array. Never repeats the immediately-preceding image (tracked via `lastSplashImage`).

**The `<picture>` `<source>`-vs-`<img>` trap:** `#splash-screen` uses `<picture><source srcset="...webp"><img src="...png"></picture>`. A `<source srcset>` wins over `<img src>` — when showing a custom (data URL) image, `source.removeAttribute("srcset")` must be called explicitly or the bundled webp silently keeps showing.

**The splash frame is anchored to the artwork, not the viewport, and is sized by maxima only.** `splash-background.webp` is an ornate arch (740×1600) whose opening is a plain cream panel; the rotating image hangs on that panel in a gold border. Two rules make that hold in general rather than by coincidence, and both are easy to undo by accident:
- **`#splash-panel` is a paint-free geometry anchor** reproducing the rectangle `background-size: cover` renders the art into (`max(100vw, 100vh × 0.4625)` × `max(100vh, 100vw ÷ 0.4625)`), so the frame's percentages are percentages *of the art*. The panel's straight-walled cream runs x 15.5%–84.3%, y 48%–98.5% (measured from the art's pixels). The frame's **top edge** is pinned to 44.5% — the line where the columns' capitals meet the springing of the arch — so every image starts from the same height however tall it is, the way a picture hangs from a fixed hook; hence `top` + `translateX(-50%)` only, never the usual `translate(-50%, -50%)`, and the `splash-entrance` keyframes must match or the frame jumps when the animation ends. Caps are 58%×40%: 58% binds at the top edge, where the cream is 63.6% wide, leaving ~2.9% clearance from the painted columns. Viewport percentages only appear to work because a phone (0.462) is within a rounding error of the art's 0.4625 — a tablet is not. The background itself stays on `#splash-screen` and stays `cover`: the arch must be full-bleed on the phone, no letterbox bars. A `min-aspect-ratio: 13/20` block handles the shapes where `cover` crops the panel away, collapsing the anchor to the viewport and dropping the top edge to 50% of it (below the viewport midline is below the arch at every ratio in that range; the 44.5% capital line itself is cropped off-screen there). **That threshold is deliberately 0.65, not the art's own 0.4625** — using the art ratio shipped a real bug: an installed PWA's viewport is shorter than the screen (status bar, gesture bar), so an ordinary phone landed just *above* 0.4625, got the tablet fallback, and dropped its frame to mid-viewport, while tests on a nominal 390×844 (0.4621) squeaked under and passed. The art-anchored placement is valid while the frame's lowest edge (44.5% + 40% = 84.5%) stays visible, i.e. `50 + 50 × 0.4625/R ≥ 84.5` → up to R ≈ 0.67; 0.65 keeps margin. `tests/test-e2e.js` guards this with three same-width viewports straddling 0.4625 — keep all three.
**The splash is darshan, and its timing lives in four places that must move together.** `SPLASH_HOLD_MS` (3200) and `SPLASH_FADE_MS` (800) in `app.js`; `#splash-screen`'s `transition: opacity 0.8s` in `styles.css`, which `SPLASH_FADE_MS` times the DOM removal against (shorter, and the element vanishes mid-dissolve); and the splash wait in **nine** test suites — six name it `SPLASH_WAIT_MS` (five at 4200 to outlast HOLD + FADE, while `test-splash-custom.js`'s deliberately sits *inside* the hold at 300) and `test.js`, `test-unit.js` and `test-i18n.js` still use a bare `4200` literal. Grep for both when retuning. The picture's entrance animation eats the first 0.9s, so settled viewing is ~2.3s, not 3.2s — that's the number to reason about when tuning. `continueFromSplash()` is wired on `pointerdown` immediately (not on `load`, so an early tap on a slow first visit isn't dropped), cancels the pending timer, and is guarded against running twice. **Never describe any of this as dismissing the image** — see the `devotional-register` memory: the splash shows a deity, the user *continues* into the ledger. The `#splash-hint` line sits at 90% of the artwork, below the frame's lowest possible edge (84.5%) and above the cream's floor (98.5%), so it is never over the deity's image; if the frame's caps change, that number moves with them.

- **The frame's box is `width/height: auto` plus `max-width`/`max-height`, never a fixed width.** Given only maxima, the browser scales each bitmap to fit at its own ratio, so the box always equals the image's ratio — which is what guarantees no image is stretched, squished, cropped or letterboxed to fit the panel (Hanuman plus up to four user uploads of any shape share this box without being reshaped to it). The earlier `width: 74%; max-height: 62%` could not promise that: a tall enough image hit the height cap with its width still pinned, and `object-fit: contain` then letterboxed it inside its own gold border. `tests/test-e2e.js` and `tests/test-splash-custom.js` both assert `contentRatio === naturalRatio` and cream-panel containment; the e2e tablet case is the guard for the anchoring half specifically.

**Upload pipeline (`processSplashImage` in `app.js`) is client-side only**, tuned for two distinct constraints, not one: stored size (target ~250KB via downscale-then-encode, per `SPLASH_TARGET_BYTES`, so storage is unaffected by input size) vs. decode-time RAM (a 5MB cap and a ~40 megapixel guard, since a browser must materialize a full raw bitmap before it can downscale — file size alone is an imperfect proxy for that). Prefers `createImageBitmap(file, {resizeWidth, resizeQuality})` to downsample during decode; falls back to a plain `<img>` decode guarded by the megapixel check.

**Bootstrap sequence** (`initApp()`, async IIFE in `app.js`): request persistent storage (best-effort) → `loadLedgerFromDB()` (live store → latest backup → empty array, never seeded from `data.json` — that file is a local-testing fixture only, deliberately never auto-loaded into a real user's ledger) → `ensureRecentEntriesExist(7)` backfills null placeholders for the last 7 days → persist + fresh backup → `renderToday()`. `renderToday()` is the single entry point that re-renders Today Card + Reflection Summary + Ledger List; call it after every mutation rather than patching the DOM piecemeal. Poornima detection is entirely keyword-based (`hasExplicitPoornima()`) — a previous static-calendar fallback (`poornima.json`) was dead code (its only caller was unreachable) and has been removed.

**`todayISO` is a module-level `let`, refreshed at the top of `renderToday()`** — not a `const` computed once at script load. It used to be exactly that, and `renderLedgerList()` separately shadowed it with its own always-fresh local copy; a tab left open across midnight could then show Today Card and the Ledger List disagreeing about what "today" was. Don't reintroduce a local shadow — read the module-level one. A `document.addEventListener("visibilitychange", ...)` handler refreshes it (and re-renders) whenever the app returns to the foreground with a stale date, and a periodic `setInterval` check catches the remaining gap that transition-based refresh alone can't: a tab or PWA left continuously visible (screen never off, no app-switch) spanning a local midnight rollover, which would otherwise silently overwrite yesterday's entry instead of creating today's, since `updateTodayEntry()` looks its entry up by date.

**Notes are HTML-escaped via `escapeHTML()` everywhere they're rendered** (Today Card, ledger row edit, locked ledger row view) since they're interpolated into template strings set via `innerHTML`. The `<textarea>` cases matter most: an unescaped note containing a literal `</textarea>` would close the element early and inject real markup, not just inert text in a `<div>`. Note `escapeHTML()` does not escape `"` (unnecessary for text-node content, its only use case) — never reuse it to build a quoted HTML *attribute* value from untrusted text; set the property via JS after element creation instead (see `sankalpa-context-edit` in `renderSankalpaPage()`).

**Milestone-crossing lookups are precomputed once per `renderToday()` pass**, not per row and not per render function — `getCroreMilestone(dateISO)` re-derives the whole milestone history from scratch on every call (O(n log n)), so calling it 3× per row was O(n² log n) just for markers, and `renderReflectionSummary()`/`renderLedgerList()` were each independently calling `getMilestoneHistory(ledgerData)` on top of that. `renderToday()` now calls `getMilestoneHistory(ledgerData)` once and passes the result into both; `renderLedgerList()` builds its own `Map<date, crore>` from it for O(1) per-row lookups. `getCroreMilestone()` itself is still fine for one-off calls (e.g. `updateTodayEntry()`'s single post-save check). `celebrateMilestone()` fires from every save path that can cross a boundary — `updateTodayEntry()`, the Ledger row save handler inside `buildYearRows()`, and `addJaapToToday()` (Mala Mode). Each captures `getCroreMilestone(entry.date)` before mutating and again after, then compares via **`didCrossNewMilestone(before, after)`**. That comparison was deliberately duplicated while there were two callers and documented as such; a third took it past where that held, the same trajectory the 7-day window took before it became `EDITABLE_WINDOW_DAYS`. The check exists because `getCroreMilestone()` reports that a crossing *exists* on a date, not that this save created it — without it, re-saving an unchanged milestone entry re-fires all 96 petals.

**Notes search replaces the year accordions rather than filtering them, and its query is module-level.** `renderLedgerList()` renders a search box, then returns early into a flat, newest-first result list whenever `ledgerSearchQuery` is non-empty. It builds those results from `ledgerData` via the pure `searchLedgerNotes(entries, query)` — **not** by filtering rendered rows, which would silently miss every past year, since non-current years have no row DOM at all until expanded (see the lazy-build note). The query lives at module scope for the same reason the carousel's state would: `renderLedgerList()` is rebuilt by every save/toggle/language switch, so a local would drop the user back to the full ledger mid-search. Two consequences worth keeping: the input is destroyed and recreated on each debounced keystroke, so focus and caret are restored explicitly afterwards or the user types into a dead field; and result rows are deliberately **read-only**, keeping the 7-day edit window and its save handlers in exactly one place rather than duplicated into a second row renderer. The search box's `value` is set as a property, never interpolated into the markup — `escapeHTML()` doesn't escape quotes.

**"On this day" is deliberately silent when there's nothing to say.** `getOnThisDayEntry(referenceISO)` matches on `MM-DD` across earlier years, skips null/zero days, and returns the *nearest* year's entry; the Today Card omits the line entirely on null rather than rendering an empty prompt. 29 February finding nothing in non-leap years is correct, not a gap.

**Text size scales off the root font-size, and `user-select` is scoped rather than blanket.** Every size in `styles.css` is expressed in `rem`, so `html.text-small`/`html.text-large` (90% / 118%; "medium" is the stylesheet's own 100% and deliberately sets no class) scale the entire app coherently — which is the point, since most reading surfaces sit *below* the 16px default and an installed standalone PWA gives the user no browser chrome to zoom with. `applyTextSize()` runs at the top of `app.js`, next to the background theme, so it lands **before first paint**; applying it from `initApp()` would visibly reflow the app under the splash. One layout consequence is load-bearing: at `text-large` the date grows wide enough to collide with `.ledger-jaap`, which is normally absolutely positioned at the row's *true* centre, so that one size hands the count back to the grid's spacer column (`grid-column: 3`) where it cannot overlap by construction. `tests/test-e2e.js` guards this with a genuinely wide (6-digit) count — the check is vacuous without one, since a null entry renders a narrow "—". Separately, `body` still sets `user-select: none` so taps feel app-like, but notes, the Sankalpa display, and the totals opt back in with `user-select: text`: the blanket rule was silently preventing a sadhak from copying their own words out of the app.

**`sw.js` is what actually makes the app offline-capable — the claim was aspirational before it existed.** IndexedDB always made the *data* offline, but the shell wasn't cached, so a no-network launch depended on incidental HTTP cache; `app.js` also fetches `i18n/translations.json` on every launch, which is the entire reason that file has a retry-and-fallback path. `sw.js` precaches the critical shell (see `PRECACHE_URLS`) and serves same-origin GETs stale-while-revalidate; other same-origin assets are picked up by the runtime handler on first use rather than bloating install. Four things here are load-bearing:
- **Registration uses a relative `"./sw.js"`** (end of `app.js`). An absolute `/sw.js` would 404 and take the wrong scope on GitHub Pages, where the app lives at `/jaap-ledger/` rather than `/`.
- **The revalidation's `cache.put()` must be `return`ed** so `networkFetch` settles when the write lands, not when the response headers arrive. Without the return, `event.waitUntil(networkFetch)` covered only the fetch, so the browser could kill the worker mid-write and the cache silently never updated — the exact cache-forever failure that `waitUntil` is there to prevent, while its own comment claimed the protection.
- **Both the precache and the revalidation fetch deliberately bypass the browser's HTTP cache** (`cache: "reload"` / `cache: "no-cache"`). Without this the worker's own refresh is answered by the HTTP cache with the very bytes it's meant to replace, silently turning stale-while-revalidate into cache-*forever* — a user pinned to whatever build they first loaded, with no escape but clearing site data. This project has no build step and therefore no content-hashed filenames, so heuristic HTTP caching bites hard. `tests/test-service-worker.js` simulates a real deploy to guard this; don't remove that test.
- **Cross-origin requests are never intercepted or cached** — the Google Identity script and every `googleapis.com` Drive call are authenticated and one-shot.
- **`CACHE_VERSION` only needs bumping for renamed/removed assets.** Routine deploys don't require it; stale-while-revalidate picks changed files up on the next launch (users are at most one launch behind).

**Service workers break tests that simulate network failure, and page-level request interception cannot stop them.** `tests/test-i18n.js` aborts `i18n/translations.json` to exercise the fallback — but the worker precaches exactly that file, so it answers from cache and the failure can't happen. Puppeteer's `page.setRequestInterception` does **not** see the `sw.js` script fetch or any of the worker's own fetches, so aborting them from a `page.on("request")` handler silently does nothing. The lever that works is CDP `Network.setBypassServiceWorker`, and it requires `Network.enable` on the same session first or it's accepted and ignored (see `bypassServiceWorker()` in that file). Any future test that mocks the network at the request layer will hit this.

**The export/backup payload is a versioned object, and the legacy shape must keep importing.** `buildLedgerExportPayload(sankalpa)` emits `{version: 2, entries, sankalpa}` and is shared by the Export button, the Google Drive upload, the Firestore sync document, and (via the same `sanitizeSankalpaForExport()`) the automatic backup. Each entry carries `updatedAt` **only when it genuinely holds one** — the version stayed at 2 precisely because the field is optional, so every timestamp-free backup already sitting in a user's Drive keeps importing. Never default it: stamping an old entry "now" would make an ancient backup look freshly edited and let it win a sync it should lose — so the Sankalpa now travels with the ledger everywhere. It previously travelled nowhere: it lived in one IndexedDB store with no export, import, backup or Drive path at all, and died with the device. `parseImportedLedgerFile()` normalizes an imported file to `{entries, sankalpa}` and **still accepts a bare JSON array**, which is what every export before v2 produced — dropping that branch would make every file a user already has on disk unimportable. Both functions are deliberately pure (they take/return plain values rather than touching IndexedDB) so they're directly unit-testable, same as `shouldShowSundayBackupReminder()`/`buildDriveUploadRequest()`. Corollary: a legacy file carries no vow, so import only writes a Sankalpa when the file actually has one — otherwise importing an old export would silently wipe the user's current vow. `restoreFromBackup()` guards the same way for pre-v2 backups.

**Every path that replaces the whole ledger snapshots it *before* replacing it, never after.** Import's `saveAutomaticBackup()` runs ahead of `ledgerData = importedData`; `applyPulledLedger()` backs up the ledger it is discarding, not the one it just installed. Import had this backwards once — the backup was overwritten with the imported data in the same breath, so the replaced ledger was gone immediately — and the sync path repeated the mistake when it was first written. Keep this ordering at any new such path.

**Import snapshots the ledger *before* replacing it, never after.** `saveAutomaticBackup()` runs ahead of `ledgerData = importedData` in the import handler. It used to run after, which overwrote the only backup with the imported data in the same breath, so the replaced data was gone immediately. Keep this ordering.

**But be precise about what that snapshot buys — there is exactly one backup slot.** `saveAutomaticBackup()` writes the same `"latest"` key on *every* save, so the pre-import snapshot survives only until the next save. Restore from Backup can therefore undo a mistaken import **only if nothing has been saved since**; once the user saves an entry, the pre-import ledger is unrecoverable. An earlier version of this note (and the import handler's own comment) called the snapshot "a real escape hatch", which claimed a guarantee the code does not provide — that claim is withdrawn, deliberately, rather than implemented. Export remains the only durable escape hatch. Keeping the single slot is a decision, not an oversight; don't "fix" it into a history without asking.

**`openDB()` memoises one connection.** It used to open a fresh connection per call and never close any — a single Today Card save opens three. Leaked connections aren't just untidy: an open connection **blocks a version upgrade**, so the next `DB_VERSION` bump would hang behind them. The memo is cleared by `onversionchange` (another tab wants to upgrade — close and let it), `onclose` (eviction/corruption, so callers don't get a dead handle), and on open failure (so a transient error isn't cached for the whole session).

**`areLedgerEntriesValid(entries)` guards every path that puts foreign data into `ledgerData`** — Import, `restoreFromBackup()`, and `loadLedgerFromDB()`'s recovery branch. Only Import validated before; the other two did `Array.isArray` and nothing more, so the exact crash Import's guard exists to prevent (a non-string `notes` hitting `hasExplicitPoornima()`'s `.toLowerCase()`, killing `renderToday()` and with it the whole app) was reachable through Restore. The future-date rule stays Import-only, deliberately: rejecting a future date in a file the user just chose is reasonable, but silently discarding one already in their own backup would be data loss on a device whose clock was later corrected.

**`formatDate()`/`formatDateLong()` return `""` for anything unparseable**, and never throw. They used to emit `"undefined undefined NaN"` and `formatDate(undefined)` threw outright — reachable through a Sankalpa whose date `sanitizeSankalpaForExport()` defaulted to `""`, inside a render that would take the page down with it.

**Attribute values go through `tAttr()`, never bare `t()`.** `escapeHTML()` deliberately doesn't escape `"`, so it cannot build a quoted attribute. Every such attribute currently holds a translated string and no dictionary entry contains a quote — but that's a fact about today's content, not about the code, and one future translation with a quotation mark would break out of the attribute.

**The milestone celebration fires on a *newly created* crossing, not an existing one.** Both save paths capture `getCroreMilestone()` before the mutation and compare against after — that function reports that a crossing *exists*, not that this save made it, so re-saving an unchanged milestone entry (or just tapping Save twice) used to re-fire all 96 petals. Keep the two paths in step.

**Never touch `localStorage` directly — go through `readStoredPreference()` / `writeStoredPreference()`.** `app.js` is a classic script, so a throw at top-level scope aborts the **entire remaining file**: no `initApp()`, no listeners, no service worker, and a splash screen that never clears. Two real ways that happens — `setItem` throwing `QuotaExceededError` on a full origin (four ~250KB custom splash images get close), and *reading* `localStorage` at all throwing `SecurityError` when the platform blocks site data (Safari's "Block All Cookies", some webviews). The accessors degrade to the in-memory default instead; `writeStoredPreference()` returns whether the value actually persisted, so the few callers that show a quota toast still can. The exceptions that deliberately keep their own `try/catch` are `setCustomSplashImage()` (it needs rollback-on-failure semantics) and `resolveSplashCustomSlots()`/`removeCustomSplashImage()` (already guarded).

**Async click handlers must never be left un-caught, and a full-screen overlay must never depend on an `await` to become closeable.** `renderSankalpaPage()` writes all of its markup — close button included — only *after* its first `await getSankalpa()`, so a rejection there sealed the user inside an empty full-screen page with nothing to tap. Every call site now goes through `renderSankalpaPageSafely()`, which reports and closes the page. Both Sankalpa save handlers wrap `saveSankalpa()` in `try/catch` for the same reason the ledger paths do. Relatedly, `dismissSundayBackupReminder()` closes the modal **before** marking it handled: dismissal must work whatever the state of the user's storage, since a full origin is exactly when they'd be trapped.

**The Today Card's save button is unconditional.** Its entry always comes from `ensureTodayEntryExists()`, so `entry.date === todayISO` always holds — the old `todayLockedMsg` branch could never render, and had it rendered, the unguarded `getElementById("update-today").addEventListener` would have thrown mid-render and taken the Reflection Summary and Ledger List with it. The branch and its dictionary key are gone; the listener is null-guarded anyway, matching `buildYearRows()`'s `if (saveBtn)`. The 7-day window still governs *ledger rows*, via `isEditableEntry()`.

**Every IndexedDB writer resolves on `tx.oncomplete`, never on the request.** `saveLedger()` used to `await store.put(...)` — an `IDBRequest` is not a thenable, so that `await` resolved on the next microtask, *before* the transaction committed, and there was no error handler at all. Since it is the sole writer of the primary ledger store, every "Saved ✓" the app showed was unverified and every failed write was silently swallowed. All three writers (`saveLedger`, `saveSankalpa`, `saveAutomaticBackup`) now wrap the transaction in a Promise resolved on `oncomplete` and rejected on `onerror` **and `onabort`** — the abort handler matters because an abort (typically `QuotaExceededError`) does *not* fire `onerror`, and an unsettled promise would hang the caller's `await` forever, which would defeat the `try/catch` below rather than trigger it.

**Every save path catches, rolls back, and reports.** `updateTodayEntry()`, the ledger-row save handler in `buildYearRows()`, `restoreFromBackup()` and the import handler all capture the previous value *before* mutating, wrap the persist step in `try/catch`, and restore that value on failure — otherwise `entry.jaap`/`entry.notes` (assigned before the `await`) stay assigned when the write fails, leaving `ledgerData` ahead of disk so every on-screen total reflects a value that was never persisted and vanishes on next launch. Failure surfaces via `t("commonSaveFailed")` / `t("ledgerRestoreFailed")`; "Saved ✓", the draft clear, and `celebrateMilestone()` run **only** after a genuinely committed write. The Today Card path deliberately does *not* re-render on failure — the card keeps showing what the user typed so they can retry without retyping it.

**Unsaved Today Card input lives in `todayDraft`, at module scope.** `renderTodayCard()` rebuilds the card via `innerHTML`, so anything held only in the DOM is destroyed by any unrelated re-render — flipping Mala View, switching language, or the translations background retry firing ~100s after launch with no user action. Same reason `ledgerSearchQuery` is module-level. It holds **raw input strings** (`{jaap, notes}`), not a parsed value: this is what the user typed, in whatever unit was active, and it isn't ledger data until a save commits. Three consequences: the Mala View toggle handler **converts** the draft's count into the new unit via `jaapToMala()`/`malaToJaap()` rather than letting the same digits be reinterpreted (540 jaap silently becoming 540 mala); focus and caret are restored after each rebuild, as `wireLedgerSearchInput()` already does; and `renderToday()` clears the draft on a date rollover, so a card left open across midnight can't drop yesterday's half-written text into today's entry. Cleared only on a successful save.

**`isValidJaapValue(value)` guards every write to `entry.jaap`** — null (no entry) or any finite, non-negative number is valid; anything else (most concretely, `NaN` from `computeJaapFromInput()` parsing a non-numeric raw value) is rejected with a toast (`t("commonInvalidNumber")`) and the save is aborted before `saveLedger()`/`saveAutomaticBackup()` run. Both save paths (Today Card, Ledger row) call this before persisting — an unguarded write would silently poison every downstream sum (lifetime/yearly totals, milestone %, pace predictions) with no error surfaced, since IndexedDB's structured clone (unlike JSON) preserves `NaN` faithfully.

**`renderLedgerList()` only eagerly builds row DOM for the current (expanded-by-default) year** — other years' `.ledger-year-container` start empty with `dataset.built = "false"`; `buildYearRows()` builds a year's rows (and wires their save/chevron listeners) the first time that year is actually expanded (its header click or "Jump to year"), then leaves `dataset.built = "true"` so re-collapsing/re-expanding within the same render pass doesn't rebuild it. Since `renderLedgerList()` still fully rebuilds on every `renderToday()` call, this only helps the *common* case (a save touching one year's data on a ledger with several years of history) — it doesn't eliminate DOM churn on saves that visibly affect an already-expanded non-current year. Tests asserting ledger row counts across multiple years must expand the target year first (via its header, not "Jump to year" — that handler collapses every other year) or the assertion will only see the current year's rows.

**7-day editable window** means today plus the six days before it, and now lives in exactly one place: `EDITABLE_WINDOW_DAYS` with `isEditableEntry()` expressed as `isWithinLastNDays(dateISO, EDITABLE_WINDOW_DAYS - 1)`. It previously delegated to `isWithinLastNDays(dateISO, 7)`, whose inclusive `<= days` accepted offsets 0–7 — **eight** days, one more than documented and one more than `ensureRecentEntriesExist(7)` ever creates. `isWithinLastNDays()` itself is deliberately unchanged: its inclusive reading is defensible and `tests/test-unit.js` asserts it directly, so the fix belongs in the caller. The ledger row save handler **re-checks `isEditableEntry()` at save time**, not only at render time — a row opened at 23:59 and saved at 00:01 is editing a day that has since aged out, which the render-time check cannot see.

**The three chrome controls each sit where they do for a measured reason.** `#app-controls` is one fixed flex row holding the Jaap/Mala pill and the gear — DOM order is screen order, so neither needs to know its neighbour's width (the pill is variable-width, and the pair of hand-tuned `right` offsets it replaced did). **Mala Mode is deliberately a floating button (`#mala-mode-fab`, bottom-right) rather than a third control in that row:** at `html.text-large` the app title and a three-control header overlap by ~33px, measured, in all three languages — both sides scale with `rem`, so the collision can't be tuned away. Its `z-index: 8000` sits above content but below the drawer (9000), the Sankalpa page (9700) and every modal, and `#ledger-list` carries `padding-bottom` so the last row isn't permanently hidden beneath it.

**`#ledger-heading` lives in `index.html`, deliberately OUTSIDE `#ledger-list`.** `renderLedgerList()` opens with `container.innerHTML = ""`, so a heading placed inside would be destroyed on the first save, toggle or language switch. Being static markup also means `applyStaticTranslations()` drives it, which keeps readable English on screen if `translations.json` fails. The same reasoning applies to the Settings version line — see the release checklist below for why that literal has no test that can catch it going stale.

**Mala Mode and Mala View are different features and are constantly confused.** *Mala View* is the header toggle (`malaViewEnabled`, `toggleMala*` keys) that changes how counts are **displayed**. *Mala Mode* is the full-screen bead counter (`#mala-page`, `malaMode*` keys) — an **input method**. Keep them apart in i18n keys, CSS and prose.

**Mala Mode deliberately has no session store and does not bump `DB_VERSION`.** Each completed mala commits straight into today's entry via `addJaapToToday(n)`; the remainder commits on exit. An earlier design added a `mala-session` IndexedDB store and was dropped, correctly — this arrangement keeps *all* I/O off the tap path (one write per 108 taps, not per tap), leaves the export payload at `version: 2` and the schema at 4 so **existing Drive backups keep importing both ways**, and bounds an app kill to losing one incomplete mala, which is what losing your place on a physical mala costs anyway. It also removes the entire "Continue Session / Start Fresh" restore flow Sumiran needs. A `DB_VERSION` bump would have carried its own hazard here: `indexedDB.open()` with a version *lower* than the stored one fires `VersionError`, and this app's stale-while-revalidate service worker deliberately serves the previous build on the launch after a deploy — so old code meeting an upgraded DB drops into `loadLedgerFromDB()`'s recovery branch and shows an empty ledger. `tests/test-mala-mode.js` pins the payload shape against exactly this.

**`addJaapToToday()` must clear `todayDraft`, and this is the subtlest hazard in the feature.** The draft prefills the Today Card, so a count typed but not saved would be written back over a mala session. Worse than an overwrite: `computeJaapFromInput("")` returns `null`, and `null` is a **valid** jaap, so a stale draft can blank the whole day rather than merely replace a number. Clearing it also discards unsaved *notes*, which is why opening Mala Mode warns first when a draft exists. The helper returns whether the write committed, and callers must treat `false` as "those beads are still uncounted" — a tap on a full dial retries the commit instead of counting a 109th bead, and Exit refuses to close while a write is failing rather than dropping the session.

**Both Mala Mode stat numbers derive from the ledger, never from a session counter** — reopening after a completed sitting shows the day's malas, not zero. `malaSessionMalas` survives only to word the exit toast.

**The Mala Mode backdrop's geometry is measured, not eyeballed.** `icons/bg-mala-mode.jpeg` (740×1600, the same 0.4625 ratio as the splash art, so `cover` behaves identically) is a dark arch niche on cream. The contiguous dark run through its centre is 7.7% wide at y=8%, 32.3% at y=14%, 52% at y=16%, reaching x 9.3%–90.5% only below ~30%. The deity frame is ~32% of the screen width, hence the stack starting at 15%. Two controls were placed in that upper region and **vanished** — a translucent light pill on the painted cream — which is why the buttons carry their own opaque dark ground and Exit sits at the foot of the stack rather than the top corner. Everything here is light-on-dark; the app's maroon-on-cream palette is invisible against `rgb(72,41,23)`.

**Mala View is a presentation-layer toggle only** (`computeJaapFromInput()` handles the conversion both ways) — it never mutates stored jaap values. Exports always emit raw jaap regardless of the toggle. Watch the precision guard: if a user leaves a pre-filled floored mala value unchanged but the original stored jaap wasn't an exact multiple of 108 (a legacy fractional entry), the original is preserved exactly rather than being recomputed and silently truncated.

**CSS design tokens** live as custom properties on `:root` in `styles.css` (`--maroon`, `--gold`, `--gold-hairline`, `--cream`, `--surface`, `--font-heading`, `--font-body`, `--ease-premium`, etc. — the "Temple Gold & Maroon" theme). New themed UI should draw from these tokens rather than hardcoding colors.

**Fonts are self-hosted, never CDN-linked** — Playfair Display (`--font-heading`) and Inter (`--font-body`) live as variable-font `.woff2` files under `fonts/`, each declared once via `@font-face` with a `font-weight: 400 700` range so a single file covers every weight in use (no CDN dependency, consistent with the app's fully-offline architecture). Form controls (`input`/`button`/`textarea`/`select`) don't inherit `body`'s font-family in browser UA stylesheets by default, so there's an explicit `font-family: inherit` reset for them — remove it and counts/labels/buttons silently fall back to the platform UI font.

**Background themes** (Alpana/Mandala/Jharokha) render on a dedicated fixed `#app-background` element via `body.bg-*` classes — not `background-attachment: fixed` on `body`, which iOS Safari has historically degraded. The splash screen deliberately never applies the chosen background theme; it always uses its own dedicated backdrop.

**Google Drive backup is one of the app's two network dependencies** (Sync is the other — see below), and only when a user actually engages with it (`app.js`, "Google Drive Backup" section, near the end of the file). `loadGoogleIdentityScript()` lazily injects `https://accounts.google.com/gsi/client` on first use — the rest of the app stays fully offline-capable. `GOOGLE_DRIVE_CLIENT_ID` is a hardcoded, real, public OAuth Client ID (public by design — client IDs for browser apps aren't secrets); see [README.md#google-drive-backup-setup](README.md) if it ever needs to be recreated. The `drive.file` scope means the app can only see/manage files it created itself. Three logic pieces are deliberately pure and side-effect-free so they're directly unit-testable without mocking the network: `shouldShowSundayBackupReminder(dateISO, lastPromptDateISO)` (`isSunday(dateISO) && lastPromptDateISO !== dateISO`), `buildLedgerExportPayload()` (shared with the plain Export button), and `buildDriveUploadRequest(existingFileId, payloadJSON)` (decides PATCH-media-update vs. POST-multipart-create). `lastSundayBackupPromptDate` in localStorage is a display-state flag like `backgroundChoice`, not practice data — deliberately excluded from Export/Import/backup-restore. The bootstrap check lives in `initApp()` after the initial `renderToday()`, not inside `renderToday()` itself (which also runs after every save) — the reminder is an app-open event, not a re-render event. **On phone/PWA testing over a LAN IP** (per the "Test on a phone" command above): Google's OAuth console rejects raw IP-address origins outright ("must end with a public top-level domain") — there's no way to authorize `http://<LAN-IP>:3333` for Drive sign-in. Test Drive backup via `localhost` (already an authorized origin) or the deployed `https://arijeetkundu.github.io` origin instead; everything else in the app works fine over a LAN IP.

**Sync across devices is the app's second network dependency, and its model is settled: a save pushes, opening the app pulls.** One document per sadhak at `users/{uid}/ledger/current`, holding exactly `buildLedgerExportPayload()`'s output — so a pulled ledger is parsed by `parseImportedLedgerFile()` and vetted by `areLedgerEntriesValid()`, the same guard that protects Import and Restore. Per-date merging with last-write-wins was proposed and **rejected by the user**; don't re-open it. Five things here are load-bearing:
- **`signInForSync()` must never become `async`.** Browsers permit `window.open()` only synchronously inside a user gesture, so everything through `signInWithPopup()` runs in the click's own task. The first attempt awaited the SDK fetch first; the gesture was spent, Safari silently refused the popup, and Firebase hung forever — no error, no popup, a permanently dead button, which is why this shipped broken and had to be reverted. `prepareSyncSdk()` warms the SDK when the Settings drawer opens instead, and the button stays disabled showing `syncPreparing` until `firebaseAuthReady` holds the **resolved** SDK. A popup-availability probe was removed deliberately: browsers allow roughly one `window.open` per gesture, so probing can consume the allowance the real popup needs.
- **Never compare payloads with `JSON.stringify()`.** Firestore returns a document's keys in *alphabetical* order, not the order they were written, so an identical ledger compares unequal — the app announced "updated from your other device" on every single return to the foreground. `ledgerSignature()` compares content via arrays at every level, sorted by date, immune to both key order and row order.
- **`applyPulledLedger()` compares *after* backfilling, not before.** A pull runs `ensureRecentEntriesExist(7)`, so the local ledger legitimately ends up holding placeholder days the stored one has never had — permanently. Comparing the raw pull against local would report a difference on every open forever. The question is whether the ledger this pull would *produce* differs from the one already here.
- **The push hooks into `saveLedger()`'s `tx.oncomplete`** — the sole writer of the ledger store, so every save path is covered by construction rather than by remembering to call it in each one. It fires only on a committed transaction, and is deliberately not awaited (a save must feel instant and work offline). A failed push sets a **persisted** flag, since the case it exists for is a save made offline, where the app is likely closed before the network returns; the next open pushes before it pulls. `syncApplyingRemote` guards the echo — applying a pull writes to IndexedDB, which is where the push hook lives.
- **The first device to sync seeds the store; every later device pulls it down and replaces what it had.** That is inherent to the chosen model, not a bug — but it means a device holding real practice must sign in *first*. `applyPulledLedger()` snapshots the ledger it replaces **before** replacing it (same ordering the import handler learned; see below), but there is one backup slot, so Export stays the only durable escape hatch. Uses the Firestore **lite** build (135KB vs 443KB) — one-shot get/set is all this model wants; offline is already handled by IndexedDB.

**i18n (English/Hindi/Bangla) is reviewed, locked content plus a small lookup layer** — `i18n/translations.json` (~155 keys, each `{en, hi, bn}`, `{placeholder}` tokens for dynamic values) is the single source of truth; don't inline any of it back into `app.js` (a prior draft did this and was deliberately reverted — the dictionary must stay a separate, fetchable JSON asset). `app.js` loads it once via `loadTranslations()` (one automatic retry on immediate fetch failure) into a module-level `TRANSLATIONS`, and every render function/toast/dialog calls `t(key, params)` to look strings up, falling back to English, then to the raw key string as an absolute last resort. **That last-resort fallback must never reach static markup**: `applyStaticTranslations()` (drives every `data-i18n`/`-aria`/`-title`/`-placeholder` element in `index.html`) deliberately leaves an element's baked-in English text untouched when `TRANSLATIONS` has no real entry for its key, rather than overwriting good English with a raw key name — this is what keeps a `translations.json` load failure from making the whole UI look broken. If both initial attempts fail, `scheduleTranslationsRetry()` keeps retrying the fetch in the background (5s interval, capped at 20 attempts) — dynamic sections (Today Card, Reflection Summary, Ledger List, Sankalpa) do show the raw key string in the meantime, since they're rebuilt from scratch each render with no prior DOM to preserve, but self-correct with a full re-render as soon as a background retry succeeds, without needing a reload. `formatDate()`'s short "D MMM YYYY" form (Ledger List, Pace predictions, Milestones list, Sankalpa date) stays in English in every language, deliberately — only `formatDateLong()`'s weekday + full month name (Today Card date line only) translates, via `datesWeekdaysFull`/`datesMonthsFull` in the dictionary. Numerals stay Western (0-9) everywhere. The first-run language picker (`#language-picker`) and the Settings-drawer switcher (`#lang-settings-wrap`) both call the same `applyAppLanguage(lang)`, which persists to `localStorage["appLanguage"]` (guarded against quota errors, unlike most other `localStorage.setItem()` calls in the file) and re-renders everything in place — no reload needed, and language selection applies immediately on tap (no separate "Continue" step).

## Testing conventions (see existing `tests/*.js` before adding new assertions)

- Puppeteer-driven, run against a real served instance — no mocking of the DOM or storage.
- Fixed phone viewport (390×844) is set explicitly in `test-e2e.js`; Puppeteer's 800×600 default breaks viewport-relative layout assertions (e.g. the splash frame).
- Tests needing deterministic image selection mock `Math.random` via `page.evaluateOnNewDocument` in an isolated `browser.createBrowserContext()`, so the override and localStorage state never leak into other sections sharing the main page.
- `confirm()`/`alert()` dialogs default to auto-accepted via a single `page.on("dialog", ...)` handler gated on a shared mutable flag (`shouldAcceptDialogs` in `test-e2e.js`) — a test that needs to exercise a declined dialog flips the flag temporarily rather than registering a second, competing listener.
- File uploads use `elementHandle.uploadFile(tmpPath)` against the real (hidden) `<input type="file">`, with fixture images generated at test time via `sharp` (a devDependency, also used for asset prep).
- Top-level `function`/`let` declarations in `app.js` are reachable from `page.evaluate()` even though it's a classic (non-module) script — tests call app.js internals directly (e.g. `pendingSplashSlot`, milestone/formatting functions) rather than only driving the UI.

## Workflow expectations (from project history)

- `data.json` is a local-testing fixture only — the app never fetches or auto-loads it into a real user's ledger (a fresh/empty ledger always starts blank). It also carries an intentional local modification on this machine that must never be staged or committed — always exclude it explicitly (`git add <specific files>`, never `git add -A`/`.`).
- Every feature/fix goes on its own branch; run the full `npm test` suite before considering work done; the user manually verifies on their installed PWA (Safari → Add to Home Screen) before anything merges to `main`; pushes to GitHub only happen on the user's explicit instruction, never automatically.
- The two `.docx` deliverables (`Sumiran-Lite-Technical-Documentation.docx`, `Sumiran-Lite-User-Guide.docx`) cannot be hand-edited as text — they're zip-packaged XML. Regenerate them with a `python-docx` script that opens the existing file as a template, clears the body, and rebuilds content, so theme/fonts/styles are preserved.
- **Always** do any fix or enhancement on its own branch, never directly on `main`. Once development is done, add relevant tests (unit and/or E2E) and run the suite until everything is green. Ask for explicit permission before merging to `main`; once merged, run the full suite again on `main` and fix/re-test/re-commit if anything regresses. Before merging or pushing, give the user the option to test manually (local or installed PWA). Once confirmed working, update documentation as needed (README, CLAUDE.md, both `.docx` deliverables), commit and then ask for explicit approval before pushing to GitHub. After pushing, clean up by deleting the branch the work was done on, once confirmed safe to do so (fully merged). For releases: bump the tag by `0.0.1` for a minor change, or to the next whole number (e.g. `2.0.0` → `3.0.0`) for a major one — **and bump `#app-version` in `index.html` to match**. That string is a hand-maintained literal (no build step, no `version` field anywhere to derive it from), so nothing but this checklist keeps it honest; `tests/test.js` guards its *shape*, not its value, so a stale version passes every test.
