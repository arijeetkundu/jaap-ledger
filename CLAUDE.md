# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sumiran Lite is an offline-first Progressive Web App for logging daily "jaap" (mantra repetition count). Single-page vanilla JavaScript, no framework, no build step — `index.html`, `app.js`, `styles.css` are served as static files as-is. Live at https://arijeetkundu.github.io/jaap-ledger/, deployed via GitHub Pages from the `main` branch root.

## Commands

```bash
# Run locally (serve over HTTP — IndexedDB/PWA installability are unreliable on file://)
python -m http.server 3333
# open http://localhost:3333

# Test on a phone on the same Wi-Fi: http://<LAN-IP>:3333 (different origin from localhost — no shared IndexedDB/localStorage)

# Install test tooling
npm install

# Run the full test suite (requires the server above running in another terminal)
npm test

# Run a single suite
node tests/test.js              # structural smoke tests
node tests/test-unit.js         # pure-logic unit tests
node tests/test-e2e.js          # full user-flow E2E tests
node tests/test-redesign.js     # design tokens, milestone celebration, motion
node tests/test-splash-custom.js # custom splash image upload/rotation/delete
node tests/test-sunday-backup.js # Sunday backup modal + Google Drive backup (mocked network)
node tests/test-i18n.js         # language picker, Settings switcher, translations-load-failure fallback
node tests/test-service-worker.js # offline launch, precache, deploy pickup, shortcut target
```

There is no build step, linter, or CI pipeline — `npm test` must be run locally before pushing. 378 assertions across the 8 suites as of this writing.

## Architecture

**No modules.** All functions in `app.js` are top-level, global, and hoisted — execution order in the file matters (later code assumes earlier functions/constants already exist). There's no import/export boundary; naming collisions are prevented only by convention.

**Two-tier storage, strictly separated by purpose:**
- **IndexedDB** (`jaap-ledger-db`, `DB_VERSION` in `app.js`) holds practice data only, across 4 object stores: `ledger` (live entries), `ledger-backups` (latest auto-backup, overwritten each save), `meta` (currently unused — was a one-time data.json seeding guard, now dead schema kept per the never-destroy-stores rule below), `sankalpa` (single vow record). The upgrade handler is additive-only — bump `DB_VERSION` and add a store only if needed; never destroy existing stores.
- **localStorage** holds display preferences and device-local assets only, never practice data: `malaViewEnabled`, `backgroundChoice`, `lastSplashImage`, `splashImage:custom0`..`custom3`, `appLanguage`, `lastSundayBackupPromptDate`, `lastDriveBackupAt`, `textSize`. Export/Import and the automatic backup cover the IndexedDB **ledger and Sankalpa** only — localStorage content is deliberately excluded and never round-trips through backup/restore. Note `lastSundayBackupPromptDate` (the Sunday prompt was dealt with — written by a successful upload *and* by every dismiss path, so it cannot tell you whether a backup happened) and `lastDriveBackupAt` (written *only* on a genuinely successful upload) are separate keys for exactly that reason — don't conflate them.

**Splash screen rotation runs synchronously before first paint.** A `chooseSplashImage()` IIFE at the top of `app.js` resolves the image pool and sets `#splash-img`/`#splash-source` before the async `initApp()` bootstrap even starts. Hanuman (`splash/hanuman-splash.*`) is a fixed constant, always in the pool, never stored, never replaceable. Up to 4 additional slots are user-uploaded photos; a slot's filled/empty state is simply whether `localStorage["splashImage:customN"]` holds a valid `data:image/` URL — there's no separate metadata array. Never repeats the immediately-preceding image (tracked via `lastSplashImage`).

**The `<picture>` `<source>`-vs-`<img>` trap:** `#splash-screen` uses `<picture><source srcset="...webp"><img src="...png"></picture>`. A `<source srcset>` wins over `<img src>` — when showing a custom (data URL) image, `source.removeAttribute("srcset")` must be called explicitly or the bundled webp silently keeps showing.

**Upload pipeline (`processSplashImage` in `app.js`) is client-side only**, tuned for two distinct constraints, not one: stored size (target ~250KB via downscale-then-encode, per `SPLASH_TARGET_BYTES`, so storage is unaffected by input size) vs. decode-time RAM (a 5MB cap and a ~40 megapixel guard, since a browser must materialize a full raw bitmap before it can downscale — file size alone is an imperfect proxy for that). Prefers `createImageBitmap(file, {resizeWidth, resizeQuality})` to downsample during decode; falls back to a plain `<img>` decode guarded by the megapixel check.

**Bootstrap sequence** (`initApp()`, async IIFE in `app.js`): request persistent storage (best-effort) → `loadLedgerFromDB()` (live store → latest backup → empty array, never seeded from `data.json` — that file is a local-testing fixture only, deliberately never auto-loaded into a real user's ledger) → `ensureRecentEntriesExist(7)` backfills null placeholders for the last 7 days → persist + fresh backup → `renderToday()`. `renderToday()` is the single entry point that re-renders Today Card + Reflection Summary + Ledger List; call it after every mutation rather than patching the DOM piecemeal. Poornima detection is entirely keyword-based (`hasExplicitPoornima()`) — a previous static-calendar fallback (`poornima.json`) was dead code (its only caller was unreachable) and has been removed.

**`todayISO` is a module-level `let`, refreshed at the top of `renderToday()`** — not a `const` computed once at script load. It used to be exactly that, and `renderLedgerList()` separately shadowed it with its own always-fresh local copy; a tab left open across midnight could then show Today Card and the Ledger List disagreeing about what "today" was. Don't reintroduce a local shadow — read the module-level one. A `document.addEventListener("visibilitychange", ...)` handler refreshes it (and re-renders) whenever the app returns to the foreground with a stale date, and a periodic `setInterval` check catches the remaining gap that transition-based refresh alone can't: a tab or PWA left continuously visible (screen never off, no app-switch) spanning a local midnight rollover, which would otherwise silently overwrite yesterday's entry instead of creating today's, since `updateTodayEntry()` looks its entry up by date.

**Notes are HTML-escaped via `escapeHTML()` everywhere they're rendered** (Today Card, ledger row edit, locked ledger row view) since they're interpolated into template strings set via `innerHTML`. The `<textarea>` cases matter most: an unescaped note containing a literal `</textarea>` would close the element early and inject real markup, not just inert text in a `<div>`. Note `escapeHTML()` does not escape `"` (unnecessary for text-node content, its only use case) — never reuse it to build a quoted HTML *attribute* value from untrusted text; set the property via JS after element creation instead (see `sankalpa-context-edit` in `renderSankalpaPage()`).

**Milestone-crossing lookups are precomputed once per `renderToday()` pass**, not per row and not per render function — `getCroreMilestone(dateISO)` re-derives the whole milestone history from scratch on every call (O(n log n)), so calling it 3× per row was O(n² log n) just for markers, and `renderReflectionSummary()`/`renderLedgerList()` were each independently calling `getMilestoneHistory(ledgerData)` on top of that. `renderToday()` now calls `getMilestoneHistory(ledgerData)` once and passes the result into both; `renderLedgerList()` builds its own `Map<date, crore>` from it for O(1) per-row lookups. `getCroreMilestone()` itself is still fine for one-off calls (e.g. `updateTodayEntry()`'s single post-save check). `celebrateMilestone()` fires identically from both save paths that can cross a boundary — `updateTodayEntry()` and the Ledger row save handler inside `buildYearRows()` — keep both checks in sync if this logic changes; there's no shared helper, by the same pattern as the 7-day-editable-window duplication below.

**Text size scales off the root font-size, and `user-select` is scoped rather than blanket.** Every size in `styles.css` is expressed in `rem`, so `html.text-small`/`html.text-large` (90% / 118%; "medium" is the stylesheet's own 100% and deliberately sets no class) scale the entire app coherently — which is the point, since most reading surfaces sit *below* the 16px default and an installed standalone PWA gives the user no browser chrome to zoom with. `applyTextSize()` runs at the top of `app.js`, next to the background theme, so it lands **before first paint**; applying it from `initApp()` would visibly reflow the app under the splash. One layout consequence is load-bearing: at `text-large` the date grows wide enough to collide with `.ledger-jaap`, which is normally absolutely positioned at the row's *true* centre, so that one size hands the count back to the grid's spacer column (`grid-column: 3`) where it cannot overlap by construction. `tests/test-e2e.js` guards this with a genuinely wide (6-digit) count — the check is vacuous without one, since a null entry renders a narrow "—". Separately, `body` still sets `user-select: none` so taps feel app-like, but notes, the Sankalpa display, and the totals opt back in with `user-select: text`: the blanket rule was silently preventing a sadhak from copying their own words out of the app.

**`sw.js` is what actually makes the app offline-capable — the claim was aspirational before it existed.** IndexedDB always made the *data* offline, but the shell wasn't cached, so a no-network launch depended on incidental HTTP cache; `app.js` also fetches `i18n/translations.json` on every launch, which is the entire reason that file has a retry-and-fallback path. `sw.js` precaches the critical shell (see `PRECACHE_URLS`) and serves same-origin GETs stale-while-revalidate; other same-origin assets are picked up by the runtime handler on first use rather than bloating install. Four things here are load-bearing:
- **Registration uses a relative `"./sw.js"`** (end of `app.js`). An absolute `/sw.js` would 404 and take the wrong scope on GitHub Pages, where the app lives at `/jaap-ledger/` rather than `/`.
- **Both the precache and the revalidation fetch deliberately bypass the browser's HTTP cache** (`cache: "reload"` / `cache: "no-cache"`). Without this the worker's own refresh is answered by the HTTP cache with the very bytes it's meant to replace, silently turning stale-while-revalidate into cache-*forever* — a user pinned to whatever build they first loaded, with no escape but clearing site data. This project has no build step and therefore no content-hashed filenames, so heuristic HTTP caching bites hard. `tests/test-service-worker.js` simulates a real deploy to guard this; don't remove that test.
- **Cross-origin requests are never intercepted or cached** — the Google Identity script and every `googleapis.com` Drive call are authenticated and one-shot.
- **`CACHE_VERSION` only needs bumping for renamed/removed assets.** Routine deploys don't require it; stale-while-revalidate picks changed files up on the next launch (users are at most one launch behind).

**Service workers break tests that simulate network failure, and page-level request interception cannot stop them.** `tests/test-i18n.js` aborts `i18n/translations.json` to exercise the fallback — but the worker precaches exactly that file, so it answers from cache and the failure can't happen. Puppeteer's `page.setRequestInterception` does **not** see the `sw.js` script fetch or any of the worker's own fetches, so aborting them from a `page.on("request")` handler silently does nothing. The lever that works is CDP `Network.setBypassServiceWorker`, and it requires `Network.enable` on the same session first or it's accepted and ignored (see `bypassServiceWorker()` in that file). Any future test that mocks the network at the request layer will hit this.

**The export/backup payload is a versioned object, and the legacy shape must keep importing.** `buildLedgerExportPayload(sankalpa)` emits `{version: 2, entries, sankalpa}` and is shared by the Export button, the Google Drive upload, and (via the same `sanitizeSankalpaForExport()`) the automatic backup — so the Sankalpa now travels with the ledger everywhere. It previously travelled nowhere: it lived in one IndexedDB store with no export, import, backup or Drive path at all, and died with the device. `parseImportedLedgerFile()` normalizes an imported file to `{entries, sankalpa}` and **still accepts a bare JSON array**, which is what every export before v2 produced — dropping that branch would make every file a user already has on disk unimportable. Both functions are deliberately pure (they take/return plain values rather than touching IndexedDB) so they're directly unit-testable, same as `shouldShowSundayBackupReminder()`/`buildDriveUploadRequest()`. Corollary: a legacy file carries no vow, so import only writes a Sankalpa when the file actually has one — otherwise importing an old export would silently wipe the user's current vow. `restoreFromBackup()` guards the same way for pre-v2 backups.

**Import snapshots the ledger *before* replacing it, never after.** `saveAutomaticBackup()` runs ahead of `ledgerData = importedData` in the import handler. It used to run after, which overwrote the only backup with the imported data in the same breath — making a mistaken import permanent, since Restore from Backup would just restore the import. Keep this ordering.

**`isValidJaapValue(value)` guards every write to `entry.jaap`** — null (no entry) or any finite, non-negative number is valid; anything else (most concretely, `NaN` from `computeJaapFromInput()` parsing a non-numeric raw value) is rejected with a toast (`t("commonInvalidNumber")`) and the save is aborted before `saveLedger()`/`saveAutomaticBackup()` run. Both save paths (Today Card, Ledger row) call this before persisting — an unguarded write would silently poison every downstream sum (lifetime/yearly totals, milestone %, pace predictions) with no error surfaced, since IndexedDB's structured clone (unlike JSON) preserves `NaN` faithfully.

**`renderLedgerList()` only eagerly builds row DOM for the current (expanded-by-default) year** — other years' `.ledger-year-container` start empty with `dataset.built = "false"`; `buildYearRows()` builds a year's rows (and wires their save/chevron listeners) the first time that year is actually expanded (its header click or "Jump to year"), then leaves `dataset.built = "true"` so re-collapsing/re-expanding within the same render pass doesn't rebuild it. Since `renderLedgerList()` still fully rebuilds on every `renderToday()` call, this only helps the *common* case (a save touching one year's data on a ledger with several years of history) — it doesn't eliminate DOM churn on saves that visibly affect an already-expanded non-current year. Tests asserting ledger row counts across multiple years must expand the target year first (via its header, not "Jump to year" — that handler collapses every other year) or the assertion will only see the current year's rows.

**7-day editable window** is enforced via `isEditableEntry()` / `isWithinLastNDays()`, checked independently in two places (`app.js`) — keep both in sync when touching this logic, there's no shared constant.

**Mala View is a presentation-layer toggle only** (`computeJaapFromInput()` handles the conversion both ways) — it never mutates stored jaap values. Exports always emit raw jaap regardless of the toggle. Watch the precision guard: if a user leaves a pre-filled floored mala value unchanged but the original stored jaap wasn't an exact multiple of 108 (a legacy fractional entry), the original is preserved exactly rather than being recomputed and silently truncated.

**CSS design tokens** live as custom properties on `:root` in `styles.css` (`--maroon`, `--gold`, `--gold-hairline`, `--cream`, `--surface`, `--font-heading`, `--font-body`, `--ease-premium`, etc. — the "Temple Gold & Maroon" theme). New themed UI should draw from these tokens rather than hardcoding colors.

**Fonts are self-hosted, never CDN-linked** — Playfair Display (`--font-heading`) and Inter (`--font-body`) live as variable-font `.woff2` files under `fonts/`, each declared once via `@font-face` with a `font-weight: 400 700` range so a single file covers every weight in use (no CDN dependency, consistent with the app's fully-offline architecture). Form controls (`input`/`button`/`textarea`/`select`) don't inherit `body`'s font-family in browser UA stylesheets by default, so there's an explicit `font-family: inherit` reset for them — remove it and counts/labels/buttons silently fall back to the platform UI font.

**Background themes** (Alpana/Mandala/Jharokha) render on a dedicated fixed `#app-background` element via `body.bg-*` classes — not `background-attachment: fixed` on `body`, which iOS Safari has historically degraded. The splash screen deliberately never applies the chosen background theme; it always uses its own dedicated backdrop.

**Google Drive backup is the app's only network dependency**, and only when a user actually engages with it (`app.js`, "Google Drive Backup" section, near the end of the file). `loadGoogleIdentityScript()` lazily injects `https://accounts.google.com/gsi/client` (the app's only CDN script) on first use — the rest of the app stays fully offline-capable. `GOOGLE_DRIVE_CLIENT_ID` is a hardcoded, real, public OAuth Client ID (public by design — client IDs for browser apps aren't secrets); see [README.md#google-drive-backup-setup](README.md) if it ever needs to be recreated. The `drive.file` scope means the app can only see/manage files it created itself. Three logic pieces are deliberately pure and side-effect-free so they're directly unit-testable without mocking the network: `shouldShowSundayBackupReminder(dateISO, lastPromptDateISO)` (`isSunday(dateISO) && lastPromptDateISO !== dateISO`), `buildLedgerExportPayload()` (shared with the plain Export button), and `buildDriveUploadRequest(existingFileId, payloadJSON)` (decides PATCH-media-update vs. POST-multipart-create). `lastSundayBackupPromptDate` in localStorage is a display-state flag like `backgroundChoice`, not practice data — deliberately excluded from Export/Import/backup-restore. The bootstrap check lives in `initApp()` after the initial `renderToday()`, not inside `renderToday()` itself (which also runs after every save) — the reminder is an app-open event, not a re-render event. **On phone/PWA testing over a LAN IP** (per the "Test on a phone" command above): Google's OAuth console rejects raw IP-address origins outright ("must end with a public top-level domain") — there's no way to authorize `http://<LAN-IP>:3333` for Drive sign-in. Test Drive backup via `localhost` (already an authorized origin) or the deployed `https://arijeetkundu.github.io` origin instead; everything else in the app works fine over a LAN IP.

**i18n (English/Hindi/Bangla) is reviewed, locked content plus a small lookup layer** — `i18n/translations.json` (~105 keys, each `{en, hi, bn}`, `{placeholder}` tokens for dynamic values) is the single source of truth; don't inline any of it back into `app.js` (a prior draft did this and was deliberately reverted — the dictionary must stay a separate, fetchable JSON asset). `app.js` loads it once via `loadTranslations()` (one automatic retry on immediate fetch failure) into a module-level `TRANSLATIONS`, and every render function/toast/dialog calls `t(key, params)` to look strings up, falling back to English, then to the raw key string as an absolute last resort. **That last-resort fallback must never reach static markup**: `applyStaticTranslations()` (drives every `data-i18n`/`-aria`/`-title`/`-placeholder` element in `index.html`) deliberately leaves an element's baked-in English text untouched when `TRANSLATIONS` has no real entry for its key, rather than overwriting good English with a raw key name — this is what keeps a `translations.json` load failure from making the whole UI look broken. If both initial attempts fail, `scheduleTranslationsRetry()` keeps retrying the fetch in the background (5s interval, capped at 20 attempts) — dynamic sections (Today Card, Reflection Summary, Ledger List, Sankalpa) do show the raw key string in the meantime, since they're rebuilt from scratch each render with no prior DOM to preserve, but self-correct with a full re-render as soon as a background retry succeeds, without needing a reload. `formatDate()`'s short "D MMM YYYY" form (Ledger List, Pace predictions, Milestones list, Sankalpa date) stays in English in every language, deliberately — only `formatDateLong()`'s weekday + full month name (Today Card date line only) translates, via `datesWeekdaysFull`/`datesMonthsFull` in the dictionary. Numerals stay Western (0-9) everywhere. The first-run language picker (`#language-picker`) and the Settings-drawer switcher (`#lang-settings-wrap`) both call the same `applyAppLanguage(lang)`, which persists to `localStorage["appLanguage"]` (guarded against quota errors, unlike most other `localStorage.setItem()` calls in the file) and re-renders everything in place — no reload needed, and language selection applies immediately on tap (no separate "Continue" step).

## Testing conventions (see existing `tests/*.js` before adding new assertions)

- Puppeteer-driven, run against a real served instance — no mocking of the DOM or storage.
- Fixed phone viewport (390×844) is set explicitly in `test-e2e.js`; Puppeteer's 800×600 default breaks viewport-relative layout assertions (e.g. the splash frame).
- Tests needing deterministic image selection mock `Math.random` via `page.evaluateOnNewDocument` in an isolated `browser.createBrowserContext()`, so the override and localStorage state never leak into other sections sharing the main page.
- `confirm()`/`alert()` dialogs default to auto-accepted via a single `page.on("dialog", ...)` handler gated on a shared mutable flag (`shouldAcceptDialogs` in `test-e2e.js`) — a test that needs to exercise a declined dialog flips the flag temporarily rather than registering a second, competing listener.
- File uploads use `elementHandle.uploadFile(tmpPath)` against the real (hidden) `<input type="file">`, with fixture images generated at test time via `sharp` (a devDependency, also used for asset prep).
- Top-level `function`/`let` declarations in `app.js` are reachable from `page.evaluate()` even though it's a classic (non-module) script — tests call app.js internals directly (e.g. `pendingSplashSlot`, milestone/formatting functions) rather than only driving the UI.

## Workflow expectations (from project history)

- `data.json` is a local-testing fixture only — the app never fetches or auto-loads it into a real user's ledger (a fresh/empty ledger always starts blank). It also carries an intentional local modification on this machine that must never be staged or committed — always exclude it explicitly (`git add <specific files>`, never `git add -A`/`.`).
- Every feature/fix goes on its own branch; run the full `npm test` suite before considering work done; the user manually verifies on their installed PWA (Safari → Add to Home Screen) before anything merges to `main`; pushes to GitHub only happen on the user's explicit instruction, never automatically.
- The two `.docx` deliverables (`Sumiran-Lite-Technical-Documentation.docx`, `Sumiran-Lite-User-Guide.docx`) cannot be hand-edited as text — they're zip-packaged XML. Regenerate them with a `python-docx` script that opens the existing file as a template, clears the body, and rebuilds content, so theme/fonts/styles are preserved.
- **Always** do any fix or enhancement on its own branch, never directly on `main`. Once development is done, add relevant tests (unit and/or E2E) and run the suite until everything is green. Ask for explicit permission before merging to `main`; once merged, run the full suite again on `main` and fix/re-test/re-commit if anything regresses. Before merging or pushing, give the user the option to test manually (local or installed PWA). Once confirmed working, update documentation as needed (README, CLAUDE.md, both `.docx` deliverables), commit and then ask for explicit approval before pushing to GitHub. After pushing, clean up by deleting the branch the work was done on, once confirmed safe to do so (fully merged). For releases: bump the tag by `0.0.1` for a minor change, or to the next whole number (e.g. `2.0.0` → `3.0.0`) for a major one.
